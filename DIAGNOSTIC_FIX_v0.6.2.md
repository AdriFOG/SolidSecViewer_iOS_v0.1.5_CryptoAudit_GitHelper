SOLIDSEC VIEWER iOS v0.6.2 — SELF-TEST INTEGRITY FIX
=====================================================

v0.6.1 DIAGNOSTICS
------------------
selftest=failure
packages=success
pctest=success
iosbuild=success
validate=success
warningguard=success

Xcode ended with:
  ** BUILD SUCCEEDED **

Solid compatibility test:
  SOLIDSEC SELFTEST: OK

Private Vault failure:
  PRIVATE VAULT SELFTEST: FAIL - Un blob con chunks reordenados fue aceptado

ROOT CAUSE
----------
This was a self-test fixture bug, not a production AES-GCM failure.

The test generated its large plaintext with a byte pattern that repeats every
256 bytes. PrivateVaultCrypto.chunkSize is 1 MiB, which is an exact multiple
of 256. That accidentally made the first two complete plaintext chunks
byte-for-byte identical.

The test then swapped those two valid encrypted frames. Because their plaintext
was identical, swapping them did not change the recovered file or its SHA-256.
The test incorrectly interpreted that as failure to detect reordering.

v0.6.2 FIX
----------
The fixture now incorporates the chunk ordinal into the generated bytes and
asserts that chunk 0 and chunk 1 differ before encryption.

The reorder test now performs two explicit checks:
1. Reordered intact frames without expected index integrity data must produce
   plaintext different from the original fixture.
2. The same reordered file WITH expectedPlaintextSize + expectedSHA256 must
   throw PrivateVaultCryptoError.integrityMismatch.

PRODUCTION CRYPTO
-----------------
No production Private Vault cryptography was changed.

The intended model remains:
- AES-256-GCM authentication for each 1 MiB outer-vault chunk;
- encrypted index stores expected plaintext byte size and SHA-256;
- indexed reads verify both values;
- whole-file SHA-256 therefore detects loss/substitution/reordering of otherwise
  individually valid legacy SSVB0001 frames.
